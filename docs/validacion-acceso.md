# Validación de acceso, permisos y doble factor

CRM-013 añade pruebas de integración repetibles en `apps/api/test/auth-validation.integration.test.ts`. Ejecutarlas con `npm run db:check` únicamente contra una base de pruebas aislada, nunca sobre la base con datos reales: el comando `db:seed` carga datos ficticios y las pruebas modifican sus propios registros. La ejecución de integración también forma parte de CI. Se recomienda validar las nuevas rutas cada vez que cambien permisos o se incorporen operaciones.

## Alcance comprobado

- Alta de un administrador ficticio mediante el modelo existente y establecimiento de contraseña con el comando administrativo. La aplicación no tiene una pantalla de alta de usuarios.
- Configuración TOTP mediante el comando interactivo real con un código generado durante la prueba; el código inicial no se puede reutilizar para iniciar sesión, el secreto queda cifrado y un código posterior permite el acceso. Los cálculos TOTP también se contrastan con los vectores RFC 6238.
- Un código inválido no activa MFA. Un restablecimiento fallido conserva el secreto y la sesión existente; uno correcto cambia el secreto, revoca las sesiones y queda registrado en auditoría. El proceso requiere acceso autorizado a la consola del servidor, `CRM_AUDIT_ACTOR_ID` de un administrador activo de la organización y control del nuevo autenticador. La identidad del ejecutor es declarada por la persona con acceso a la consola, no autenticada automáticamente.
- Contraseña incorrecta, bloqueo tras cinco fallos, rechazo de credenciales correctas durante el bloqueo y acceso posterior al vencimiento simulado; inicio, cierre y revocación, vencimiento simulado en la base, y rechazo de sesiones de usuarios u organizaciones deshabilitados.
- Operador y administrador pueden consultar conversaciones de su organización; el operador puede registrar notas y cambiar asignación/estado de su organización. Se rechazan consultas y cambios de conversaciones de otra organización, la asignación a un usuario externo y operaciones administrativas de canales y auditoría para operadores. El administrador tampoco puede operar un canal de otra organización. Las pruebas de CRM-009 cubren el envío restringido al responsable y los casos de envío a conversaciones de otra organización.

La prueba genera TOTP desde código y verifica su compatibilidad con vectores conocidos; **no sustituye** una prueba manual de registro y acceso con la aplicación autenticadora elegida en el dispositivo del administrador. La prueba de bloqueo mueve el reloj almacenado en PostgreSQL para evitar esperar quince minutos; no simula el paso real de ese tiempo. Las pruebas se ejecutan sin WhatsApp real y no certifican funciones que aún no existen.

## Revisión previa a producción

- **HTTPS:** la plantilla `deploy/nginx.conf.example` aún no equivale a un entorno publicado. Antes de usar datos reales, instalar certificados válidos, verificar redirección HTTP→HTTPS, renovación y acceso a frontend y API por el mismo origen; impedir el acceso público directo a la API y PostgreSQL. Consultar `docs/security-operations.md`.
- **Secretos:** cargar claves distintas y persistentes de MFA y WhatsApp desde un gestor autorizado, restringir los permisos del proceso y los respaldos, verificar restauración y rotación. El token en `sessionStorage` es accesible al JavaScript de la página: revisar XSS y la política de contenido antes de publicar.
- **Recuperación de MFA:** no hay recuperación automática ni códigos de respaldo. El procedimiento administrativo requiere acceso privilegiado a consola y la clave de cifrado de MFA; verificar identidad por un canal independiente, registrar el responsable y comprobar la revocación de sesiones. Si la clave de cifrado se pierde, será necesario volver a registrar el segundo factor de cada administrador. Probar este procedimiento con la aplicación autenticadora elegida antes de producción.
- **Intentos fallidos:** la aplicación bloquea la identidad durante 15 minutos después de cinco fallos en una ventana de 15 minutos; puede bloquear a un usuario legítimo si un tercero conoce su correo. Aplicar límites y monitoreo adicionales por origen en la infraestructura, con protección contra intentos distribuidos y sin exponer credenciales ni datos personales en logs. Definir procedimiento de atención ante bloqueo y probarlo con el proxy real. El límite por origen todavía no está implementado ni verificado.
- **Permisos:** no crear rutas nuevas sin autenticación y filtros de organización en el servidor. Repetir las pruebas para cada recurso y acción nueva. La separación actual no restringe qué conversaciones de la misma organización puede leer un operador.

Estas medidas de despliegue son pendientes operativos, no se activan ni se verifican por las pruebas locales. No habilitar el uso con datos reales hasta completar la revisión correspondiente.
